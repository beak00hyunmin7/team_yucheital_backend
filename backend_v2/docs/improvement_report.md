# 백엔드 성능·구조 개선 보고서

## 적용 원칙

기존 `app/`, `compose.yaml`, DB 테이블을 변경하지 않았습니다. 새 구현은
`backend_v2/`와 새 CI 파일에만 추가되어 기존 API와 병행 검증할 수 있습니다.

## 주요 변경

### 1. 추론 경로

기존 경로는 원본과 평활 지형을 최대 3회씩 예측하여 요청당 최대 6회의 추론이
가능했습니다. v2는 `(전처리 해시, 체크포인트 해시, rain_mm, time_s)`가 같은 요청을
하나의 결과로 취급하고 캐시 미스당 정확히 한 번 추론합니다.

AI 입력용 등고선 렌더링도 예측 함수 안에서 반복하지 않습니다. 업로드 전처리 때 한 번
만들어 `model_input.png`로 저장하고 이후 조건이 다른 예측에서 재사용합니다.

### 2. 모델 호환성과 장애 처리

현재 제공된 v5 모델의 FiLM `cond_dim=2` 구조를 포함한 U-Net을 추가했습니다. 로더가
가중치에서 입력 채널, 기본 채널 수, FiLM 차원을 확인하며 RGB·2조건 계약이 아니면
거부합니다. `torch.load(..., weights_only=True)`를 사용하고 체크포인트 SHA-256을 모델
버전과 캐시 키에 기록합니다.

모델 로딩 실패 시 D8을 실행하지 않습니다. liveness는 유지하되 readiness와 예측은
503으로 실패하여 운영자가 가짜 AI 결과를 정상 결과로 오인하지 않도록 했습니다.

### 3. 배수구 처리

v2에는 D8 흐름누적, 저지대 점수, 후보 간격 선택 또는 자동 배수구 추천이 없습니다.
AI 예측은 배수맵·수심 지표까지만 반환합니다. 시나리오 DB에는 사용자가 보낸 좌표만
`source=USER`로 저장합니다.

기본 시나리오 평가기는 용량 제한 근사임을 버전과 경고로 명시합니다. 위치를 추천하지
않으며, 학습된 surrogate가 준비되면 동일 인터페이스로 교체할 수 있습니다.

### 4. 파일과 CSV

원본, 모델 입력, 정규화 고도 배열, 배수맵, 수심 배열, 시나리오 맵을 별도 파일로
저장하되 upload/result/scenario ID로 연결합니다. 파일 쓰기는 임시 파일을 완전히 쓴 뒤
원자적으로 교체합니다.

배수구 좌표와 지표는 검색·비교가 가능한 DB를 원본으로 사용합니다. CSV는 별도 중복
보관하지 않고 내보내기 요청 때 생성합니다.

### 5. DB·캐시

- 기존 테이블과 충돌하지 않는 `v2_` 테이블 사용
- 업로드·예측·시나리오 캐시 키 unique 적용
- 상태·생성시각과 부모 ID·생성시각 복합 인덱스 적용
- Alembic 마이그레이션 추가
- 프로세스 내부 single-flight로 같은 작업의 동시 중복 실행 방지
- 처리 단계·지연·캐시·오류 코드를 `v2_processing_runs`에 기록

### 6. 렌더링·응답

AI가 생성한 256×256 배수맵을 그대로 제공합니다. 원본 크기의 overlay PNG를 매 요청
만들지 않으며 프론트가 정규화 좌표로 배수구 레이어를 그리도록 했습니다. Base64 이미지를
응답 JSON에 넣지 않아 응답 크기와 메모리 복사를 줄였습니다.

수심 RGB 역변환은 256색 LUT 전체를 모든 픽셀에 브로드캐스트하지 않습니다. SciPy
`cKDTree`를 사용하고, SciPy가 없으면 제한된 크기의 chunk 계산으로 메모리 사용량을
통제합니다.

## 의도적으로 남긴 과제

- 일반 등고선 이미지에서 실제 고도값을 복원하는 OCR·선 연결·보간 모듈
- 학습된 배수구 시나리오 surrogate
- Redis 등 다중 프로세스·다중 서버 분산 락
- S3/MinIO 구현체와 CDN
- 사용자 인증·인가와 rate limit
- DB·파일의 일관된 백업 자동화
- 실제 GPU 환경의 부하·OOM·p95 시험

위 항목은 모델 또는 운영 인프라가 없는 상태에서 임의로 구현하지 않고 인터페이스와
확장 지점만 마련했습니다.
